## פיירברי, מה שכבר אומת בשטח

**בסיס:** `https://api.fireberry.com` · header **`tokenid`**, בלי `Bearer`.

**המבנה הנכון של `POST /api/v3/query`:**
```json
{ "objectType": 1051,
  "fields": [{"name":"name"},{"name":"pcfStatus"}],
  "pageSize": 500, "pageNumber": 1,
  "filter": [{"type":"and","conditions":[
     {"fieldName":"modifiedon","operator":"ge","value":"2026-08-01 00:00:00"}]}] }
```
התשובה **שטוחה**: `{data:[…], success, pageNumber, pageSize, isLastPage}`. העטיפה הכפולה שמתועדת בפלייבוק היא ארטיפקט של Make, לא של ה-API.

### חמש מלכודות שעלו מבדיקה חיה

1. 🔴 **מפתח בקשה לא מוכר, פיירברי מתעלם ממנו בשקט.** `sort`, `query`, `filters` כולם החזירו `200` עם **כל** הרשומות, בלי סינון ובלי שגיאה. **כל שאילתה מסוננת חדשה חייבת בדיקת שלילה.** `sort` לא נתמך בכלל, ממיינים אצלנו.
2. 🔴 **תווית של lookup משתנה בין אובייקטים.** אובייקט `4` מחזיר `ownername`, אובייקט `1051` מחזיר `owneridname`. הגנה: הטריגר `fill_owner_label` על 7 טבלאות משלים מתוך `raw`.
3. 🔴 **`1039.pcfNextPaymentDate` מפיל את פיירברי ב-HTTP 500**, גם לבדו. הוצא מהמיפוי. ב-`fb-sync` יש הסרת שדות אוטומטית על `Invalid field`.
4. שדות שנראים קיימים ואינם: `1.pcfCity` (יש `billingcity`) · `67.name` (יש `campaignname`) · `9.systemuserid` (יש `crmuserid`, ו-`_id` תמיד עובד).
5. `POST /api/query` הישן **כן** מחזיר `isrequired` / `isreadonly` / `maxlength` בבלוק `Columns[]`, בניגוד למה שכתוב בפלייבוק.
