## 1. ממצאי האימות החי — הפרוטוקול הטכני המאומת

**כל מה שכאן נבדק היום מול `https://api.fireberry.com` עם ה-tokenid של רויטל. אפס כתיבות.**

### 1.1 המבנה הנכון של `POST /api/v3/query` — סוגר סתירה פתוחה מס' 1

```json
{
  "objectType": 1051,
  "fields": [ {"name":"name"}, {"name":"pcfStatus"}, {"name":"modifiedon"} ],
  "pageSize": 500,
  "pageNumber": 1,
  "filter": [
    { "type": "and",
      "conditions": [
        { "fieldName": "modifiedon", "operator": "ge", "value": "2026-08-01" }
      ] }
  ]
}
```

| רכיב | הצורה הנכונה | מה שנוסה ונכשל |
|---|---|---|
| `fields` | **מערך של אובייקטים** `[{"name":"..."}]` | מחרוזת CSV → `400 Invalid fields`. מערך מחרוזות → `400`. |
| `filter` | **מערך** של קבוצות, כל קבוצה `{type, conditions[]}` | `{fieldName,operator,value}` ישירות → `400 Missing property: type`. `{type,...}` בלי conditions → `400 Missing property: conditions`. |
| `objectType` | **מספר**, camelCase | מחרוזת `"1051"` → `400`. |
| מבנה התשובה | `{ "data":[...], "success":true, "pageNumber":n, "pageSize":n, "isLastPage":bool }` | **התשובה שטוחה.** ה"עטיפה הכפולה" `{data:{data:[]}}` שתועדה בפלייבוק היא **ארטיפקט של מודול Make, לא של ה-API.** |

### 1.2 🔴 הגוצ'ה המסוכנת ביותר שגיליתי — **מפתח לא מוכר מתעלמים ממנו בשקט**

שלחתי `"query":"(pcfStatus = 99)"`, `"filters":[...]`, ו-`"sort":[{...}]`. **כל השלושה חזרו `200 OK` עם כל הרשומות** — בלי סינון, בלי מיון, בלי שגיאה.

> **הכלל התפעולי:** כל שאילתה חדשה חייבת **בדיקת שלילה** — להריץ אותה עם ערך שאמור להחזיר אפס, ולוודא שהיא באמת מחזירה אפס. אם היא מחזירה נתונים — הסינון לא נתמך והתעלמו ממנו. זו סכנה חמורה יותר מ"אפס תוצאות בשקט": כאן אתה מקבל **יותר מדי** נתונים ומחשב מדד שגוי בלי לדעת.
> **`sort` לא נתמך בשום צורה שבדקתי.** המיון נעשה אצלנו, לא בפיירברי.

### 1.3 picklists ו-lookups חוזרים בשתי הצורות — פער הקריאה/כתיבה נפתר

```json
{ "statuscode": 2, "status": "ליד חדש",
  "pcfProduct": "2F73403A-…", "pcfProductname": "סדנה בוסט",
  "ownerid": "0FA826FA-…",   "ownername": "ויטרו ראשי",
  "pcfStatus": 2,            "pcfStatusname": "ליווי בתהליך",
  "_id": "CBDA6AAF-…" }
```

**כלל השמות:** `statuscode` → התווית ב-`status`; `ownerid` → `ownername`; כל שדה אחר `X` → `Xname`. **מסננים ומדדים תמיד על המספר. תצוגה תמיד מהתווית.**

### 1.4 שדות מקושרים (linked fields) — ✅ מאומת, לא רק תחבירית

`pcfaccountid_accountname` ו-`pcfaccountid_telephone1` על אובייקט 1051 החזירו **ערכים מלאים**. זה חוסך קריאה שנייה לכל רשומה — קריטי לדריל-דאון של דשבורד 5.

### 1.5 בונוס — `POST /api/query` (Legacy) **כן** מחזיר חובה/readonly/maxlength

הפלייבוק קובע ש-`mandatory`/`readonly`/`maxlength` **אינם נחשפים ב-API כלל**. זה לא מדויק. הנתיב ה-Legacy מחזיר בלוק `Columns[]` ובו לכל שדה:

```json
{"name":"סטטוס ליווי","fieldname":"pcfStatus","isprimaryfield":false,
 "isrequired":false,"isreadonly":false,"maxlength":null}
```

> 📌 **פעולה למייק:** זה אומר שאפשר לייצר אוטומטית את טבלת שדות החובה במקום לספור ידנית. לא נוגע לדשבורד — אבל שווה עדכון בפלייבוק ובתהליך העבודה על השדות.

### 6.2 למה לא לקרוא לפיירברי ישירות מהדשבורד

| בעיה | קריאה ישירה | מחסן |
|---|---|---|
| Rate limit | כל רענון של כל משתמשת = עשרות קריאות | קריאות רק בסנכרון |
| מהירות טעינה | 10–30 שניות | < 300ms |
| **מגמות היסטוריות** | **בלתי אפשרי** — פיירברי מחזיק רק את המצב הנוכחי | snapshot יומי = היסטוריה אמיתית |
| חישובים חוצי-אובייקטים | join ב-JavaScript בדפדפן | SQL |
| חשיפת טוקן | ה-proxy הוא endpoint ציבורי לכל ה-CRM | הטוקן לא יוצא מה-VPS |
| נפילת פיירברי | הדשבורד מת | הדשבורד עובד על הדאטה מאתמול |

> ⭐ **הנימוק שמכריע: היסטוריה.** "כמה לקוחות היו בליווי ב-1 ביוני" — פיירברי **לא יודע לענות**, כי הוא מחזיק רק את הסטטוס הנוכחי. בלי snapshot יומי משלנו, כל מדד מגמה בדשבורד הוא שקר. זו לא אופטימיזציה, זו דרישה פונקציונלית.

### 6.3 אסטרטגיית הסנכרון

**Backfill ראשוני (פעם אחת):** משיכה מלאה של 19 אובייקטים ≈ **20 קריאות**, ~40 שניות.

**סנכרון יומי (04:30 שעון ישראל):**
```
לכל אובייקט:
  filter: [{type:"and", conditions:[
      {fieldName:"modifiedon", operator:"ge", value: <last_sync − 1 שעה>}]}]
  pageSize: 500 · עמוד אחרי עמוד עד isLastPage
```
דלתא יומית צפויה: **5–20 קריאות סה"כ.**
חלון החפיפה של שעה אחת מכסה את הבעיה הידועה שפיירברי שומר **שעה מקומית עם סיומת `Z`** — לא UTC אמיתי.

**סנכרון מיידי (כפתור):** אותו workflow, מופעל דרך webhook עם secret. **Cooldown של 3 דקות** — לחיצה נוספת מחזירה "סונכרן לפני X" בלי לקרוא ל-API.

**Snapshot היסטורי:** בסוף כל סנכרון, שורה יומית לטבלת `fact_daily_snapshot` — בליווי, פייפליין, יתרות. **זה מה שמייצר את המגמות.**

### 6.6 אימות ואבטחה

> 🔴 **תנאי סף לפריסה — לא המלצה.** בגרסת 10/08 הוצע `fb-proxy.php` עם סיסמת צד-לקוח. **סיסמת JS היא לא אבטחה** — ה-hash גלוי ב"הצג מקור", וה-proxy הוא endpoint ציבורי לקריאת כל ה-CRM. הארכיטקטורה כאן מבטלת את הבעיה מהשורש: **הדשבורד לא יכול לקרוא לפיירברי בכלל.**
