## 1. איך השיוך בין הרשומות עובד

זה לב המנוע. שלוש שכבות.

### שכבה 1 · טבלת ההצלבה (crosswalk)

פיירברי לא מאפשר לקבוע GUID בעצמנו — הוא מייצר מזהה חדש לכל רשומה. לכן המנוע מחזיק טבלה אחת:

```
אובייקט ישן + GUID ישן   →   GUID חדש
1     / A3F2-…            →   9BC1-…
1003  / 77E4-…            →   7E20-…
```

כל רשומה שנוצרת מוסיפה שורה לטבלה — **לפני** שנוגעים ברשומה שתלויה בה.

### שכבה 2 · סדר טעינה טופולוגי — אב לפני בן

```
לקוח (1)
   └── תהליך מכירה (4)
          └── תשלום (1039)
                 └── תיעוד תשלום (1018)   × N לפי מספר התשלומים

  כל אחד מהם נושא גם קישור ישיר ללקוחה, לא רק לאב הישיר
```

בפועל, לשורת תשלום אחת מהמערכת הישנה:

1. **לקוח** נוצר ראשון → הטבלה מקבלת `1/A3F2… ← 9BC1…`
2. **תהליך מכירה** נוצר, בשדה "לקוחה - מקושר" נכתב `9BC1…` → הטבלה מקבלת `4/77E4… ← 4D77…`
3. **תשלום (1039)** נוצר עם *שני* קישורים — לקוחה `9BC1…` ותהליך מכירה `4D77…` → הטבלה מקבלת `1039/77E4… ← 7E20…`
4. **תיעודי תשלום (1018)** נוצרים עם *שלושה* קישורים — לקוחה, תהליך מכירה, ותשלום `7E20…`

כל קישור הוא GUID שנשלף מהטבלה. **אף פעם לא לפי שם או טלפון** — התאמה לפי שם תצוגה בפיירברי מחזירה אפס תוצאות בשקט, בלי שגיאה.

### שכבה 3 · המזהה החיצוני — עותק עמיד של הטבלה בתוך ה-CRM

כל רשומה שנוצרת נושאת בשדה **"מזהה מערכת חיצונית 1"** את ה-GUID שלה מהמערכת הישנה. שלוש תועלות:

- **מניעת כפילויות** — לפני כל אצווה שואלים את החדשה "מי מהמזהים האלה כבר קיים אצלך", ומדלגים עליהם
- **הרצה חוזרת בטוחה** — אפשר להריץ את המיגרציה פעמיים בלי ליצור כפילות אחת. זה מה שמאפשר להתאושש מכשל באמצע בלי ניקוי ידני
- **שחזור** — אם קובץ הטבלה נעלם, בונים אותו מחדש בקריאה אחת לכל אובייקט

### רשומות יתומות

11 תשלומים ו-1,800 שיחות טלפון בלי לקוח מקושר במערכת הישנה. הכלל: **הרשומה עוברת בלי הקישור ומקבלת תיוג**, ובסוף מופק דוח "רשומות יתומות" לאישור. לא ממציאים אב, לא זורקים רשומה.

⚠️ **כלל בטיחות:** בפיירברי אסור לכתוב שדה lookup ריק — זה מחזיר 403 ומפיל את הבקשה. שדה קישור שאין לו ערך פשוט לא נשלח.

## 2. התשלומים — המודל המלא

### מה מצאתי בנתונים

בדקתי את כל 7,255 רשומות התשלום. **כל שורה היא עסקה שלמה, לא תשלום בודד.** תוכנית של 10 תשלומים מיוצגת בשורה אחת. שלושה סוגים:

| סוג | שורות | מבנה |
|---|---|---|
| **רגיל** | 5,551 | תשלום אחד. "סכום התשלום" = "סכום כולל" |
| **תשלומים** | 894 | פריסה. "סכום כולל" = הסכום המלא, "מספר תשלומים" = N |
| **הוראת קבע** | 630 | חיוב חודשי בודד שבוצע בפועל |

🔴 **מלכודת שנמצאה:** ב-210 מתוך 894 שורות הפריסה, שדה "סכום התשלום" מכיל את **הסכום הכולל** ולא את סכום התשלום הבודד. חישוב תמים לפי אותו שדה היה מנפח את המחזור מ-₪5.1M ל-₪9.7M. **הכלל שנקבע: סכום כל תיעוד = "סכום כולל" חלקי N.** אחרי התיקון הסכומים מתאזנים לשקל.

### חוקיות היצירה — לפי WF-20, ענף A

**רשומת תשלום (1039)** — אחת לכל שורה במערכת הישנה:

| שדה | ערך |
|---|---|
| `name` | `התשלום של {לקוחה} \| {מוצר} \| {סכום} ₪ \| {N} תשלומים` |
| `pcfStatus` | **2** נפרע בהצלחה — אם כל התשלומים בעבר · **1** בתהליך פירעון — אם נותרו עתידיים |
| `pcfAccountid` · `pcfSale` · `ownerid` | מטבלת ההצלבה |
| `pcfPaymentType` | מ"סוג טרנזקציה": אשראי→1 · Bit→6 · הו"ק→7 |
| `pcfNumberOfPayments` | N (בהוראת קבע: **0**, לפי האפיון) |
| `pcfNeedToPayIncludingVat` | הסכום הכולל |
| `pcftaxincludecode` | 1 (כן) |
| `pcfFirstPaymentDate` | תאריך ביצוע התשלום מהישן |
| `pcfID` | קוד הטרנזקציה מהישן |
| `pcfExternalSoftwareID1` | ה-GUID הישן |
| `pcfCreatedByPersonOrSystem` | 2 (מערכת) |

**תיעודי תשלום (1018)** — N לכל רשומת תשלום:

| שדה | ערך |
|---|---|
| `name` | `תיעוד התשלום של {לקוחה} \| {מוצר}` |
| `pcfPaymentCollection` | → רשומת התשלום (מטבלת ההצלבה) |
| `pcfPaymetStatus` | **1** נפרע בהצלחה — אם תאריך החיוב עבר · **3** ממתין לפירעון — אם עתידי |
| `pcfPaymentDate` | תאריך החיוב — **רק בנפרעים.** בממתינים השדה לא נכתב כלל |
| `pcfPayedIncludingVAT` | סכום כולל ÷ N |
| `pcfReference` | האסמכתא מהישן |

**לוח החיובים:** תשלום i נופל על *תאריך החיוב הראשון + (i−1) חודשים*. תאריך שעבר את היום → נפרע. עתידי → ממתין.

> 🔴 `pcfPaymetStatus` — **`Paymet` בלי `n`.** כך זה בפיירברי. כל קוד שכותב `pcfPaymentStatus` ייכשל בשקט.

**הוראת קבע:** 630 החיובים מתקבצים ל-**619 הוראות קבע** (לפי לקוחה + מוצר + סכום חודשי). כל אחת מקבלת רשומת תשלום עם אמצעי "הוראת קבע", מספר תשלומים 0, וסכום של חיוב חודש אחד — ותחתיה תיעוד תשלום לכל חיוב שבוצע בפועל.

## 6. מה יכול להשתבש

### 🔴 1. האוטומציות בחשבון החדש יידלקו על 100,000 רשומות

**התשובה:** השבתה מלאה — פיירברי + Make + n8n (כולל **WF-20**, שאחרת יגיב לרשומות התשלום שנטענות). **ולוודא שתורי Make ריקים לפני ההדלקה מחדש** — יש תקדים של 525 אירועים תקועים, 471 מהם מהעולם הישן.

### 🔴 2. שתי המערכות חיות במקביל
נכון להיום, 19/08 בשעה 12:51, נוצרו רשומות חדשות בשתיהן באותה דקה.

**התשובה:** חלון הקפאה של המערכת הישנה (קריאה בלבד) — **8 דקות בלבד**. אחריו הרצת דלתא לפי `createdon` (הסינון בצד השרת אומת ועובד) לפני המעבר הסופי.

### 🔴 3. 716 לקוחות קיימים בשתי המערכות
מתוך 725 שכבר במערכת החדשה.

**התשובה:** **המערכת החדשה מנצחת.** ברשומה קיימת נכתבים רק שדות ריקים, אף פעם לא דריסה. המזהה החיצוני מתמלא כדי לסגור את ההצלבה.

### 🟠 4. 934 אשכולות כפילויות במערכת הישנה (2,235 רשומות)
**התשובה:** איחוד לפני הטעינה — הרשומה עם הכי הרבה שדות מלאים היא הראשית, השאר תורמות רק שדות ריקים. **כל הרשומות הבנות — תשלומים, שיחות, הערות — מקושרות לראשית.** דוח איחוד לאישור לפני ביצוע.

### 🟠 5. `createdon` לא ניתן לכתיבה
כל 18,696 הלקוחות ייראו כאילו נוצרו ביום המיגרציה. דוח "לקוחות חדשים החודש" יציג 18,000.
**התשובה:** שדה תאריך ייעודי "תאריך יצירה מקורי" בכל אובייקט שמועבר, והדוחות ההיסטוריים נבנים עליו. **החלטה עסקית שממתינה ללקוחה.**

### 🟠 6. סינון שגוי מוחזר בשקט

**התשובה:** מנוע יחיד סדרתי, 65 קריאות/דקה, backoff אקספוננציאלי, ונקודות המשך שמאפשרות להמשיך מאיפה שנעצר.

## נספח — תיקונים ל-FIREBERRY_REST_PLAYBOOK

ארבעה ממצאים שאומתו בפועל וסותרים או משלימים את הפלייבוק:

1. **סתירה #1 (v3 מול legacy) — נסגרת חלקית.** שניהם עובדים. ב-v3 `fields` הוא **מערך של אובייקטים** — `[{"name":"accountid"}]`. מחרוזת CSV מחזירה 400. ב-legacy זו מחרוזת CSV.
2. **הסינון ב-v3 עובד.** התחביר: `"filter": [{"type":"AND","conditions":[{"fieldName":…,"operator":…,"value":…}]}]` · `"orderBy": [{"name":…,"order":"asc"}]`. **תחביר שגוי מוחזר בשקט בלי סינון ובלי שגיאה.**
3. **`isrequired` / `isreadonly` / `maxlength` כן נחשפים ב-API** — לא ב-`/metadata/records/{ot}/fields`, אלא במערך `Columns` בתשובת `POST /api/query` (Legacy). מבטל את הצורך לשאול על כל שדה.
4. **Batch API פעיל ברישיון של רויטל** — `POST /api/v3/record/{objectName|objectType}/batch/create` ו-`/batch/update`, עד 20 רשומות.
