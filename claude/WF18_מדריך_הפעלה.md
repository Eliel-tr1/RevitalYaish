## 2. סדר ההפעלה

### שלב א' · יצירת השדות ב-Fireberry

```bash
export FIREBERRY_TOKEN='...'
python3 src/fireberry_fields.py            # יבש — מדפיס בדיוק מה ייווצר
python3 src/fireberry_fields.py --apply    # יוצר
```

הסקריפט קורא קודם את רשימת השדות הקיימים, מדלג על מה שכבר קיים, **ועוצר עצירה מלאה בכשל הראשון**. בסוף הוא מדפיס change-log מוכן לאליאל.

### שלב ב' · Gotenberg (המרת HTML ל-PDF)

על ה-VPS, **לא חשוף החוצה** — רק ברשת הפנימית של דוקר:

```bash
docker network ls | grep -q n8n_net || docker network create n8n_net
docker run -d --name gotenberg --restart unless-stopped \
  --network n8n_net gotenberg/gotenberg:8
docker network connect n8n_net <שם-קונטיינר-n8n>   # אם אינו כבר ברשת
```

בדיקה מתוך קונטיינר n8n: `curl -s -o /dev/null -w '%{http_code}' http://gotenberg:3000/health` → `200`.

> **למה לא שירות חיצוני:** עמוד 2 של הדוח מכיל שמות של לקוחות. אין סיבה שהם יעברו דרך צד שלישי.

### שלב ג' · העלאת ה-workflow

```bash
export N8N_API_KEY='...'
python3 src/deploy_n8n.py            # יבש — בודק חיבור ומגבה
python3 src/deploy_n8n.py --apply    # מגבה הכל ואז מעלה, כבוי
```

### שלב ד' · חיבור ידני בממשק (חובה — credentials לא עוברים ב-API)

1. `Revital Yaish new CRM` (Header Auth, header `tokenid`) → **כל צמתי Fireberry**
2. `Zoom S2S` (Basic Auth: user = `client_id`, password = `client_secret`) → צומת **טוקן זום**
3. SMTP → צומת **מייל לרויטל ולעודד**
4. בצומת **קונפיגורציה** למלא: `ZOOM_ACCOUNT_ID` · `ZOOM_WEBINAR_ID` · `REPORT_EMAILS` · `MAIL_FROM` · `ALERT_TASK_OWNER_ID`

### שלב ה' · ריצה יבשה

`DRY_RUN` נשאר `true`. מריצים ידנית ברביעי אחרי 22:00.
**מה שאמור לקרות:** הכל נמשך, הדוח וה-PDF נוצרים, **אפס כתיבה ל-CRM, אפס מייל**.
מצליבים ידנית מול דוח הנוכחות בממשק זום.

### שלב ו' · העלאה לאוויר

לפי הסדר הזה בלבד:

1. להדליק את **הערה על המחזור**
2. להדליק את **עדכון שדות המחזור**
3. להדליק את **מייל לרויטל ולעודד**
4. `DRY_RUN → false`
5. להפעיל את ה-workflow

> 🔴 **הסדר לא שרירותי.** `pcfWebinarInstanceUuid` הוא מפתח האידמפוטנטיות: ברגע שנכתב, המופע לא יימשך שוב לעולם. לכן ההערה נכתבת **לפני** השדות. הפוך = כשל בהערה מייצר אובדן נתונים שקט. אותו עיקרון בדיוק כמו ב-WF-16.

**שלב ב' (נוכחות פר-לקוחה על 1030) נשאר כבוי** עד ש-6.6/6.6a עולים ו-1030 מתחיל להתמלא.

## 3. שלושה באגים אמיתיים שנתפסו בבנייה

**1. המספרים נעלמים מה-PDF — בלי שום שגיאה.**
מנוע ההדפסה מסתיר טקסט בזמן טעינת פונט (block period). הפונט העברי לא מכיל ספרות, הספרות נופלות לפונט השני, והוא עדיין נטען → **כל המספרים בדוח יוצאים ריקים.** ה-PDF תקין, בגודל סביר, ופשוט בלי נתונים.
**תוקן** ב-`font-display:swap` בכל `@font-face` + `waitForExpression: document.fonts.status === 'loaded'` ב-Gotenberg. יש בדיקת רגרסיה שנכשלת אם מישהו יסיר את זה.

**2. כניסה חוזרת מנפחת את הנוכחות ב-20–40%.**
משתתפת שהתנתקה וחזרה מופיעה 2–4 פעמים ב-API. סכימה נאיבית של `duration` נותנת "משך ממוצע" שקרי כלפי מעלה, ו"מספר משתתפות" מנופח. המנוע מאחד לפי זהות **ומאחד גם קטעי זמן חופפים**. יש בדיקה ייעודית.

**3. פונטים מ-CDN.**
ניסיון ראשון השתמש ב-Google Fonts. הסביבה חסמה SSL, הפונט לא ירד, והתוצאה הייתה ריבועים — **בלי שגיאה**. הפונטים מוטמעים היום ב-base64 בתוך ה-HTML (15KB אחרי subsetting של הספרות). אפס תלות ברשת.

## 5. בדיקות הקבלה — מה לבדוק בריצה הראשונה

1. **הצלבה ידנית** — מספר המשתתפות בדוח מול ממשק זום. חייב להיות זהה.
2. **בדיקת שלילה** — משתתפת שיצאה וחזרה מופיעה **פעם אחת** בטבלה. מופיעה פעמיים → מנוע האיחוד שבור, **עצור הכל**.
3. **אידמפוטנטיות** — הרצה חוזרת מיידית: אפס כתיבות, אפס מיילים.
4. **עברית ב-PDF** — לפתוח ולוודא שהמספרים לא ריקים ושאין ריבועים.
5. **שיעור הזיהוי** — אם פחות מ-60% מהמשתתפות זוהו כלקוחות, זה הסימן להדליק הרשמה בזום עם לינק אישי.

## 6. הדבר היחיד שאני ממליץ להוסיף מיד

**הרשמה בזום עם `join_url` אישי לכל לקוחה.**
היום, עם לינק סטטי אחד, הזיהוי נשען על שם מוקלד — ובסימולציה נראה בדיוק למה זה שביר: משתתפת שנכנסה בשם "iPhone של מיטל" זוהתה **רק** כי היה לה `registrant_id` עם טלפון. בלי הרשמה, היא נספרת כ"לא זוהתה".

המנוע כבר תומך בזה מלא: הוא מחפש שאלה מותאמת בשם "טלפון" בטופס ההרשמה, מנרמל ל-`972…`, ומצליב מול הלקוחה. **צריך רק להדליק את ההרשמה בזום ולהוסיף שאלת טלפון.** שאר הקוד כבר כתוב.
